# セルフ登録と管理者ダッシュボード（検証用）

## 変更範囲
- `signup.html`: メール＋12文字以上のパスワードでセルフ登録。メール認証設定が有効な環境では確認メールを案内する。
- `index.html`: クラウド同期欄から登録画面に移動。
- `admin.html`: 管理者認証後に登録者数・同期利用者数・7/30日以内のクラウド書込利用者数・解答と完了セットの件数を表示。
- `supabase/migrations/20261109_self_signup_admin.sql`: 既存のユーザー別RLSポリシーを保ったまま新規登録者を同期許可リストへ登録するトリガー、管理者限定の集計RPCを追加。

## 重要
このPRを正式版にマージしない限り、公開中の正式版は変更されない。
**SQLは現時点で共有Supabaseに適用していない。** 画面のみ公開すると、新規登録者は同期許可されず、管理画面の集計RPCも利用できない。

## 検証手順（共有環境ではなく別の検証用Supabaseプロジェクトを推奨）
1. 新たに検証用Supabaseを用意し、現行同期用のテーブル・RLSを再現する。個人の実履歴を複製しない。
2. 新しい検証用プロジェクトでスキーマ変更を適用し、テスト用Auth管理者を作成した後にそのUUIDを `app_admins` に登録する（本番のUUIDは使用しない）。
3. Supabase AuthのEmail providerを有効化。メール確認・送信制限・リダイレクト許可URL・SMTPを確認。Authのサインアップを許可する。
4. `staging-config.js` の空のURL・公開用publishable keyを検証用プロジェクトの値に変更し、Vercel Preview環境では `GKENTEI_STAGING_SUPABASE_URL` と `GKENTEI_STAGING_PUBLISHABLE_KEY` に同じ検証用プロジェクトの値を設定する。正式版プロジェクトのURLは拒否される。
5. 新規ユーザーでサインアップ→確認メール→ログイン→明示的同期許可→解答・完了セット同期を確認。
6. 他人の解答履歴・完了セットが読めないこと、一般ユーザーがadmin_sync_overview RPCを呼ぶと403になることを確認。
7. 管理者の集計値が実データと一致すること、一般利用者は管理者ダッシュボードに入れないことを確認。
8. 既存アカウントのログイン、履歴、完了セット、ローカル利用、バックアップ、同期の回帰テストを実施。
9. 登録の乱用対策（メール確認・レート制限・CAPTCHA・必要に応じ登録制限）を確認してから正式版へ。

## 留意点
- この第一段階ではユーザー一覧・削除・停止機能は作らず、総数集計だけを表示する。
- 集計用RPCは管理者登録テーブルをサーバー側でチェックする。一般ユーザーに全件データを公開しない。
- 7日/30日アクティブ数は「クラウドに新たにデータ保存したユーザー」。ログイン人数や閲覧人数とは異なる。
- 既存の承認済みユーザーや履歴レコードを変更・削除するSQLは含まない。

## 2026-11-09 追加の安全措置
- 検証用Supabase設定が空ならセルフ登録・管理画面・同期は停止し、同期用APIも503を返す。
- 検証用のフロントエンドとAPIでは正式版SupabaseプロジェクトIDを明示的に拒否する。
- 検証版のセッション・同意キーを正式版と別名に変更した。
- 10件のコード静的チェックに合格。これらは実ブラウザの認証/RLS E2E試験を代替しない。
- Vercelアクセスにはチーム認可が必要。現時点で実デプロイと認証テストは未完了。
